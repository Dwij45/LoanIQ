# System architecture

## What this is, and isn't

A **rule-based** eligibility engine, not a machine-learning model. It
has no training data, learns nothing from outcomes, and makes no
prediction of what a real lender would actually decide — every result
it produces traces back to one specific row in `data/rules.csv`, with a
source URL, a date, and a confidence tag a reader can check. See
`docs/limitations.md` for the full list of scope limits and modeling
trade-offs; this document covers how the pieces fit together.

## The four-stage pipeline

Every lender is evaluated independently through the same four stages.
`rank_lenders()` runs this once per lender, then sorts the results.

```
                    ┌─────────────┐
  ApplicantProfile ─┤   GATES     │─── fail ──► Decision(eligible=False, reason=<first failing rule>)
                    └──────┬──────┘
                           │ pass
                    ┌──────▼──────┐
                    │   AMOUNT    │  computes the eligible loan amount
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   PRICE     │  assigns the real CIBIL-based rate,
                    └──────┬──────┘  computes EMI, total interest, total cost
                           │
                    ┌──────▼──────┐
                    │    RANK     │  (across all 20 lenders, not per-lender)
                    └─────────────┘  sort eligible lenders by total cost
```

### Stage 1 — GATES (`check_gates()`)

Walks every row in `rules.csv` for this lender except the two
amount-sizing rule types (`foir_cap`, `salary_multiple_on_disposable_income`,
which belong to Stage 2). For each row:

1. Skip it if its `condition` column doesn't apply to this applicant
   (e.g. a `min_income` row conditioned on `employer_category == 'govt'`
   is skipped for a private-sector applicant).
2. A handful of `rule_name` values get special handling because they
   can't be expressed as a plain threshold comparison:
   - **`max_age_at_maturity`** — computed as `applicant.age +
     requested_tenure_months/12`, not the applicant's current age.
   - **`requires_salary_account`** — checks the applicant's salary
     account is *with this specific lender* (`lender_id`), not merely
     that they have a salary account somewhere. (An earlier version of
     this check accepted any bank; caught by
     `test_salary_account_gate_checks_specific_lender` — see
     `docs/limitations.md`.)
   - **`allows_ntc`** — only evaluated when the applicant actually has
     zero CIBIL history (`is_ntc == True`). For an ordinary applicant
     with a real score, this rule is skipped entirely; their
     creditworthiness is judged by `min_cibil` instead. (An earlier
     version evaluated this rule unconditionally and rejected ordinary
     applicants at every lender with `allows_ntc=False`; caught by
     `test_non_ntc_applicant_not_blocked_by_allows_ntc_rule`.)
3. Everything else is a plain `>=`, `<=`, or `==` comparison between the
   applicant's corresponding field and the row's `value`.
4. **A failing row only rejects the applicant if `is_hard_cutoff` is
   true.** A failing soft row is recorded into `Decision.flags` and
   evaluation continues — it's visible, but not a disqualifier.
5. **An unrecognized condition shape or operator defaults to "passes," not
   "rejects."** The code comment in `_eval_condition()` states this
   explicitly: a data-entry gap should never silently and invisibly
   disqualify someone from a rule the engine couldn't even parse —
   failing open here is the safer default than failing closed on bad
   data.

Self-employed and pensioner applicants are rejected at the very top of
this stage, before any rule is even read — no lender in this dataset has
a parallel self-employed rule set collected (see `docs/limitations.md`).

### Stage 2 — AMOUNT (`compute_amount()`)

Determines the eligible loan amount, using one of two formulas depending
on which rule type the lender has:

- If the lender has a `salary_multiple_on_disposable_income` row
  (**IDFC, Kotak only**): `amount = multiplier × max(income − existing_emi, 0)`.
  This formula was reverse-engineered from each lender's own live
  calculator — see `docs/foir-methodology.md` §2.
- Otherwise, if the lender has a `foir_cap` row (**every other lender**):
  invert the FOIR cap into a maximum EMI, then invert the EMI formula
  into a maximum principal, using the lender's own **band midpoint rate**
  as a first-pass rate (see `docs/foir-methodology.md` §1 for why this
  doesn't introduce a hidden assumption).
- If neither rule type exists for a lender (not currently the case for
  any of the 20), the amount is sized at the lender's flat `max_loan_inr`
  and a flag is raised stating that no sizing rule was found.

The result is always clamped to the lender's own `max_loan_inr` ceiling.

### Stage 3 — PRICE (inside `evaluate_lender()`)

Once Stage 2 has fixed a principal, the lender's **real** interest rate
is assigned by linear interpolation (`assign_rate()`) between its own
two published numbers:

```
cibil <= lender's own min_cibil  → rate_max_pct   (worst rate)
cibil >= 900                      → rate_min_pct   (best rate)
in between                        → linear interpolation
```

This is a small computed function of facts the lender already publishes,
not a separately stored or guessed rate-band table — an earlier design
used a standalone `rate_bands.csv`, which was dropped as an unnecessary
extra layer of (unverifiable) assumption once this formula was adopted.

The final EMI, total interest, and processing fee are computed on the
Stage-2 principal using this real rate — `total_cost = total_interest +
processing_fee` is the number Stage 4 ranks on.

### Stage 4 — RANK (`rank_lenders()`)

Runs all four stages for every lender, splits into eligible/ineligible,
and sorts the eligible list by:

```
1. total_cost         ascending  (lower cost ranks first)
2. offered_amount      descending  (tie-break: prefer the bigger loan)
3. max_tenure_months    descending  (tie-break: prefer the longer tenure)
```

**Why rank on total cost, not advertised rate:** a 9.99% rate with a 5%
processing fee can cost more over the loan's life than an 11% rate with
no fee. Sorting on `rate_min_pct` alone would silently favor attractive
headlines over what the borrower actually pays.

**The PSU/NBFC comment:** when two eligible lenders land within 2% of
each other's `total_cost` *and* belong to different `lender_type`
sectors, a note is appended to the lower-ranked one's `flags` naming the
sector difference. This is purely informational — it is written *after*
the sort has already happened and never changes the order. The
docstring in `rank_lenders()` is explicit about this: PSU-vs-NBFC
preference is "never a silent sort key."

Ineligible lenders are appended after all eligible ones, each carrying
its own rejection `reason` and any flags collected before the rejecting
gate was hit.

## Two engines, one source of truth

`src/eligibility.py` is the reference implementation. `ui/index.html`
embeds a hand-ported JavaScript version of the same four functions
(`checkGates`, `computeAmount`, `evaluateLender`, `rankLenders`) so the
demo works entirely client-side with no backend — nothing an end user
types ever leaves their browser.

Keeping two implementations of the same logic in sync is the real risk
here, so every change to either one is checked with a small Node.js
harness that extracts the pure-function portion of `ui/index.html`
(everything except the DOM-manipulation code) and runs it against the
same test profiles used against the Python engine, comparing eligible
counts, flags, and computed amounts line-for-line. This is a manual
verification discipline, not an automated CI step — if you change either
engine, re-run that comparison before trusting the result.

The data embedded in `ui/index.html` (the `const DATA = {...}` block) is
a **snapshot** of `data/lenders.csv` + `data/rules.csv` at the time it was
last generated — it does not read the CSVs live. Any change to the CSVs
must be re-serialized into that block, or the demo will silently show
stale data. There is currently no script that automates this
re-serialization end-to-end (it was done by hand during this session,
field-mapping `lenders.csv`'s raw columns to the shorter names the JS
engine expects, and converting boolean-valued rule rows correctly —
`value_num` must stay a real boolean for `==` comparisons against
`requires_salary_account`/`allows_ntc` to work, not a stringified one).
A good next step for someone picking this up would be to write that as
a real script (parallel to `scripts/gen_docs.py`) rather than repeating
the hand process.

## Keeping docs honest

`docs/data-sources.md` and `docs/assumptions-and-estimates.md` are
**generated**, not hand-written, by `scripts/gen_docs.py` reading
directly from `data/rules.csv`/`data/lenders.csv`. This is deliberate:
hand-written documentation of "which fields are estimates" can silently
drift from the data as the CSVs change, which is exactly the kind of
silent gap this project set out to avoid. The one real bug this caught
during this project: a data-pipeline script's confidence-tagging logic
had a static override table that pre-dated a later pass adding 9 new
`foir_cap` estimates, so those 9 rows (plus two age-field estimates) were
defaulting to `confidence=official` instead of `assumed` — meaning the
"this value is an estimate" flag never fired for them. Generating the
docs straight from the CSV is what surfaced it: the "Estimated values"
section came back empty when it was known not to be. Re-run
`scripts/gen_docs.py` any time `data/rules.csv` or `data/lenders.csv`
changes, rather than hand-editing the two generated docs.
